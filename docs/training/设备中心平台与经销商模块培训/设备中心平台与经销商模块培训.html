01 / Platform positioning

平台定位：设备与渠道协作工作台

它把设备事实、经销商组织和测试操作放进同一条工作路径，让不同部门围绕同一份信息完成定位、判断和协作。

这个项目把“找信息、做判断、跨部门协作、留证据”串成一条线上工作路径。
为什么建设减少设备信息分散、测试过程不透明和问题反复确认。

01

信息分散

设备、用户、组织和服务信息分布在不同入口，跨部门沟通需要反复确认。

02

测试难追踪

经销商测试账号与设备关系不够清晰，测试过程和结果难以复核。

03

协作缺证据

问题反馈常停留在描述层面，缺少统一字段和可追溯的操作记录。

建设前找到信息靠经验，判断问题靠沟通，测试结果靠人工记忆。
→
建设目标以设备为核心对象，以组织和角色为协作边界，以状态、测试和日志形成共同证据链。
使用平台前

设备信息分散在多个入口或聊天记录中，测试账号和设备关系难以核对，问题反馈常常缺少共同证据。

→
使用平台后

按设备或经销商定位对象，按字段判断状态，按测试记录和操作日志完成跨部门协作与复核。

03 / Collaboration roles

先看事实，再找对的人

不同协作角色关注不同证据，共同完成设备运营、渠道协作和问题判断。

客

客服 / 售后

设备是否存在、激活、绑定，服务是否有效。

技

运维 / 技术支持

在线状态、心跳、网络、日志、物联网卡。

运

运营 / 产品

经销商范围、业务规则、测试数据和版本变化。

经

经销商管理

APP 测试账号、设备测试记录、账号维护。

管

超管 / 平台管理员

授权范围内的高风险操作和平台审计。

07 / Business cases

业务应用案例

把平台能力放回实际业务语境，理解它在设备运营和渠道协作中的使用价值。

Case A · 设备异常

设备离线或无法预览

从设备 ID 开始，按事实链路逐层判断。

  • 客服确认设备和用户信息
  • 技术支持查看在线、心跳、P2P/MQTT、日志
  • 运维核查服务链路、节点或同步
  • 产品判断版本、规则或已知问题
Case B · 渠道抽检

经销商需要抽检设备

通过组织范围、测试账号和设备记录完成渠道验证。

  • 确认经销商和组织范围
  • 配置渠道测试对象
  • 在 APP 中添加设备并抽检
  • 查看测试记录并沉淀结果
Case C · 后台追溯

核对账号操作过程

用平台操作日志建立跨团队共识。

  • 按日期查询日志
  • 核对操作类型、对象、操作人、时间、结果
  • 判断是否成功、重复或需要重试
  • 将日志作为业务协作依据
