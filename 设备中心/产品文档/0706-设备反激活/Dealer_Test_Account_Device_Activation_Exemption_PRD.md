# 一、需求背景

## 1.1 业务场景

设备出货后，经销商客户在正式交付消费者之前，会对收到的设备进行抽样检测。抽检人员通常通过现有APP扫描设备二维码，并完成以下操作：

1. 添加设备

2. 配置设备网络

3. 检查设备是否可以正常上线

4. 查看设备状态

5. 测试视频、音频、控制或数据上报等基础功能

6. 测试完成后删除或解绑设备

当前APP添加设备与设备正式激活共用同一条业务链路。经销商抽检人员添加设备后，系统会将该行为认定为真实用户激活。

## 1.2 当前问题

经销商不是设备的最终消费者，抽检行为不应被视为设备正式销售和真实用户激活。当前添加设备可能触发以下正式动作：

- 修改设备激活状态

- 写入设备首次激活时间

- 创建正式用户设备绑定关系

- 激活设备赠送的云存权益

- 激活正式流量套餐

- 产生真实设备激活统计

- 被其他依赖激活事件的系统消费

由此可能产生：设备首次激活时间被污染、真实用户权益提前消耗、激活统计失真，以及跨系统动作难以完整回滚等问题。

# 二、需求目标

## 2.1 核心目标

> **核心目标：**经销商使用指定测试账号添加设备时，设备能够在APP内展示并完成约定的基础测试，但不触发设备正式激活、不写入首次激活时间、不激活正式云存和流量权益，同时记录完整的测试免激活日志。

## 2.3 成功标准

- 经销商可以完成设备抽检

- 测试设备正式激活状态不变

- 首次激活时间不被写入

- 云存正式权益不提前生效

- 流量正式套餐不提前生效

- 真实用户后续能够正常首次激活

- 所有测试绑定和激活拦截均有日志可追溯

# 三、产品定义

## 3.1 “反激活”的实际含义

本需求虽然业务名称为“设备反激活”，但系统不应先执行正式激活再回滚。正确实现是在正式激活发生前识别测试账号，从源头阻止正式激活动作。

> **准确系统定义：**测试账号免激活绑定，或测试场景激活拦截。


## 3.2 测试绑定和正式绑定

| **维度**     | **正式绑定（NORMAL）** | **测试绑定（TEST）** |
|--------------|------------------------|----------------------|
| 业务含义     | 真实用户正式拥有设备   | 测试账号临时操作设备 |
| 设备列表展示 | 是                     | 是，需标记为测试设备 |
| 正式激活     | 触发                   | 不触发               |
| 首次激活时间 | 写入                   | 不写入               |
| 正式权益     | 按规则生效             | 不生效               |
| 分享与转移   | 按现有规则             | 禁止                 |
| 真实用户接管 | 不适用                 | 允许被正式绑定替换   |

# 四、第一期需求范围

## 4.1 第一期必须实现

- 经销商测试账号配置与有效期管理

- 复用现有经销商组织数据

- 用户中心账号创建或关联

- 测试权限判断

- 测试绑定关系

- 测试设备APP展示及基础测试权限

- 正式激活、首次激活时间、云存权益和流量套餐拦截

- 测试解绑

- 真实用户正式接管

- 测试免激活日志及基础查询能力

## 4.2 第一期不做

- 不开发独立经销商测试APP

- 不开发设备抽检任务中心、抽检批次和测试报告

- 不建设复杂测试会话平台或独立测试流量套餐中心

- 不建设经销商测试数据看板或复杂多级审批

- 不考虑设备品类差异

- 不支持测试账号操作已被真实用户激活的设备

- 原则上不修改设备固件

## 7.2 经销商组织状态

- 组织被停用或注销后，该组织下所有测试权限立即失效

- 不允许新增测试绑定

- 不得自动转为普通账号执行正式激活

- 已存在测试关系按规则失效或禁止继续控制

## 7.3 经销商组织与账号关系

测试账号必须关联明确的经销商组织，关系主键为 org_id + user_id；不允许存在没有组织归属的测试账号。

# 八、测试账号设计

## 8.1 第一期推荐模式

每个经销商组织配置一个或多个专用测试账号。账号创建在用户中心，测试权限配置在组织或业务权限系统中。

## 8.2 不在APP端创建账号

> **禁止方案：**APP本地创建测试账号后再同步到用户中心。该模式会形成双写、数据冲突和账号状态不一致。


正确流程：管理后台创建或选择账号 → 调用用户中心创建或查询 → 获得user_id → 关联经销商组织 → 配置测试权限 → 用户在APP正常登录。

## 8.3 已有账号和新账号处理

| **场景**           | **处理规则**                                                        |
|--------------------|---------------------------------------------------------------------|
| 用户中心已存在账号 | 返回现有user_id，关联经销商组织并新增测试权限，不重复创建账号。     |
| 用户中心不存在账号 | 管理后台调用用户中心创建账号，返回user_id后创建组织关系和测试权限。 |

## 8.4 是否在用户中心增加“测试用户”

不建议在用户中心基础用户表增加 user_type=TEST。测试身份属于带组织、有效期和审批状态的业务权限，不属于永久基础身份。

## 8.5 测试权限状态

| **状态**  | **含义**               |
|-----------|------------------------|
| PENDING   | 待审批                 |
| APPROVED  | 审批通过但未到生效时间 |
| ACTIVE    | 当前有效               |
| EXPIRED   | 已到期                 |
| SUSPENDED | 已暂停                 |
| REVOKED   | 已撤销                 |
| REJECTED  | 审批驳回               |

# 十、APP端需求

## 10.1 登录与账号信息

测试账号使用现有APP和现有登录方式。登录后APP从服务端获取 account_mode、测试权限状态、有效期、org_id 和 org_name。

## 10.2 测试账号标识

> **页面提示：**当前为设备测试账号，添加设备不会触发正式激活及正式权益。


## 10.3 权限过期提示

> **提示文案：**测试权限已失效，暂时无法添加或操作测试设备。请联系经销商管理员或平台运营人员处理。


## 10.4 扫码添加设备

APP提交登录令牌、设备二维码信息、设备SN或设备ID、APP标识、客户端版本及必要配网信息。APP不得自行提交 is_test_account=true，服务端必须根据user_id重新判断权限。

## 10.5 添加成功展示

> **成功提示：**设备添加成功。当前为测试绑定，设备尚未正式激活。


## 10.6 测试账号功能限制

| **允许**         | **禁止**                         |
|------------------|----------------------------------|
| 查看设备在线状态 | 分享设备                         |
| 查看设备基础信息 | 转移设备                         |
| 查看实时画面     | 购买云存或正式流量               |
| 验证音视频能力   | 使用云存兑换码                   |
| 执行基础控制     | 领取正式用户权益                 |
| 查看设备数据上报 | 修改正式用户归属或参加消费者活动 |

APP应隐藏或禁用不支持的功能入口，服务端仍须再次校验，不能只依赖前端隐藏。

## 10.7 结束测试

第一期复用现有删除或解绑入口。操作后TEST关系失效、设备从测试账号列表移除、测试权限撤销，正式激活状态和权益状态保持不变。

# 十一、测试权限判断规则

## 11.1 第一步：账号有效性

- 用户中心账号存在且状态正常

- 登录令牌有效

- 用户未被冻结或注销

## 11.2 第二步：专用测试账号识别

查询该用户是否存在 account_purpose=DEALER_TEST。不存在则按普通用户现有绑定流程处理；存在则继续校验测试权限。

## 11.3 第三步：测试权限有效性

- 经销商组织有效

- 审批状态通过

- 权限状态为ACTIVE

- 当前时间在有效期内

- user_id与org_id关系有效

> **关键规则：**专用测试账号权限已过期、暂停或撤销时必须拒绝添加设备，不能自动进入普通用户正式激活流程。


# 十二、测试绑定业务规则

## 12.1 测试绑定逻辑实体

系统必须存在独立的测试绑定业务语义，可在现有关系表中增加 relation_type=TEST，或建立独立测试绑定表。无论采用哪种方式，测试关系都不能被下游系统识别为正式所有权关系。

## 12.2 测试绑定状态

| **状态** | **含义**               |
|----------|------------------------|
| ACTIVE   | 当前有效               |
| UNBOUND  | 用户主动解绑           |
| EXPIRED  | 测试账号或关系到期     |
| REPLACED | 被真实用户正式绑定替代 |
| REVOKED  | 后台强制撤销           |

## 12.3 测试绑定前置条件

- 测试权限有效

- 设备存在且未正式激活

- 设备不存在正式用户关系

- 设备未处于不允许绑定的异常状态

- 当前测试账号未被禁用

## 12.4 已激活设备

测试账号扫描已正式激活设备时，拒绝测试绑定，不改变正式用户关系和设备状态，并记录拒绝日志。

## 12.5 重复扫码

同一测试账号重复扫描同一设备时，幂等返回现有有效TEST关系，不重复创建、不重复发放权限、不重复触发下游动作。

## 12.6 多测试账号并发

第一期同一设备同一时间只允许一个有效TEST关系。其他测试账号扫描时提示设备正在被其他测试账号使用。

## 12.7 TEST关系业务含义

| **允许**                  | **不允许**                           |
|---------------------------|--------------------------------------|
| 设备出现在测试账号APP列表 | 触发正式激活                         |
| 获取基础测试权限          | 表示正式所有权                       |
| 访问约定设备功能          | 分享、转移、购买正式权益或消费兑换码 |

# 十三、设备端及设备平台规则

## 13.1 设备固件

第一期原则上不修改设备固件。设备继续完成配网、连接设备平台、上报状态、接收云端控制和返回执行结果。

## 13.2 设备权限鉴权

若现有设备控制强依赖“设备已正式激活”，则设备平台鉴权条件调整为：存在有效正式绑定关系，或存在有效测试绑定关系。TEST关系只能获得基础测试权限。

## 13.3 测试权限撤销

- TEST关系失效后不再签发测试访问权限

- 已有临时访问凭证应尽快失效

- 后续请求返回无权限

- 不影响设备后续正式激活

# 十五、云存权益规则

## 15.1 固定设备ID赠送权益

设备出厂时已预先绑定的赠送云存权益应区分待生效、已生效和已过期。测试账号绑定时保持待生效，不开始计算有效期；真实用户正式激活时才生效。

## 15.2 云存兑换码

- 测试账号发起兑换时拒绝兑换

- 兑换码保持未使用

- 不绑定测试设备

- 不开始权益有效期

- 记录兑换拦截日志

## 15.3 云存生效条件

# 十八、真实用户正式接管

## 18.1 接管原则

> **接管原则：**正式用户绑定优先级高于测试绑定，但必须先完成现有正式绑定安全校验。


## 18.2 正式接管流程

1. 真实用户提交设备添加请求

2. 校验当前账号为普通用户

3. 确认设备未正式激活

4. 查询有效或历史TEST关系

5. 执行现有正式绑定安全校验

6. 校验通过后将有效TEST关系置为REPLACED

7. 撤销测试账号访问权限

8. 创建NORMAL正式用户关系

9. 执行正式激活并写入首次激活时间

10. 激活云存权益和正式流量套餐

11. 记录真实用户接管日志

12. 返回正式绑定成功

## 18.3 安全校验失败

- 不创建NORMAL关系

- 不执行正式激活

- 不激活权益

- 不自动清理当前有效TEST关系

- 返回现有绑定失败原因

## 18.4 用户体验

真实用户无需联系经销商或客服，无需手动解除测试关系，也无需感知设备曾被经销商抽检。

# 二十五、幂等与并发规则

## 25.1 测试绑定幂等

同一用户、同一设备存在有效TEST关系时，重复请求返回原关系，不重复创建、不重复发放权限、不重复记录正式拦截动作。

## 25.2 正式激活幂等

- 首次激活时间只写一次

- 云存权益不重复发放

- 流量套餐不重复激活

- 正式激活事件不重复消费

## 25.3 并发绑定

同一设备同时收到测试绑定和正式绑定请求时，正式绑定安全校验通过后正式绑定优先，TEST关系置为REPLACED，只允许生成一个NORMAL关系，正式激活只执行一次。

# 二十六、安全与风控规则

- 测试权限必须有有效期并关联经销商组织

- 后台操作必须记录操作人

- APP不能伪造测试身份

- 设备绑定服务必须实时校验测试权限

- 测试账号不能操作已正式激活设备

- 测试账号不能分享、转移或消费正式权益

- 测试权限暂停后立即禁止新增测试

- 异常高频绑定行为应记录日志

第一期可以暂不建设复杂风控策略，但应保留后续扩展能力。

# 二十七、统计指标

- 有效测试账号数量

- 经销商组织测试设备数量

- 测试绑定成功率及失败原因分布

- 测试解绑数量

- 真实用户接管数量

- 测试后正式激活转化数量

- 测试设备云存或流量误生效数量

- 测试设备首次激活时间污染数量

- 测试账号越权请求数量

> **核心质量指标：**测试场景设备正式误激活率、首次激活时间污染率、正式云存误生效率、正式流量误生效率、测试关系阻塞真实用户激活率均应为0。


# 二十八、验收用例

| **用例**                     | **预期结果**                                                                                          |
|------------------------------|-------------------------------------------------------------------------------------------------------|
| 有效测试账号添加未激活设备   | APP添加成功；展示测试设备；创建TEST关系；设备仍未激活；首次激活时间为空；云存和流量不生效；日志完整。 |
| 测试账号执行基础控制         | 允许功能可正常执行；服务端校验TEST关系；不改变正式激活状态。                                          |
| 测试账号执行分享或购买       | 服务端拒绝；不创建分享、订单或权益；记录越权日志。                                                    |
| 测试账号兑换云存码           | 拒绝兑换；兑换码不核销；不生成权益；记录拦截日志。                                                    |
| 测试账号解绑                 | TEST关系失效；设备从APP移除；访问权限撤销；正式状态和权益不变。                                       |
| 测试权限过期                 | 无法新增测试绑定；不能降级为普通激活；返回过期提示；记录日志。                                        |
| 测试账号扫描已激活设备       | 拒绝测试绑定；不影响原正式用户；记录拒绝日志。                                                        |
| 同一设备重复测试绑定         | 返回原TEST关系；不重复创建或触发动作。                                                                |
| 真实用户正式激活测试过的设备 | TEST关系置为REPLACED；创建NORMAL关系；正式激活；写首次激活时间；云存和流量生效。                      |
| 正式用户绑定校验失败         | 不创建NORMAL关系、不激活、不发权益、不清理有效TEST关系。                                              |

# 二十九、上线前检查项

1. 当前所有设备正式激活入口是否统一

2. 哪些系统订阅了正式激活事件

3. 云存权益当前真正的生效触发条件

4. 流量套餐当前真正的生效触发条件

5. APP设备列表是否可以展示TEST关系

6. 设备控制是否强依赖正式激活状态

7. 测试账号解绑后权限多久失效

8. 正式用户绑定是否能够覆盖TEST关系

9. 设备是否依赖正式流量套餐才能联网

10. 保修、返佣、销售统计、CRM等系统是否也依赖激活事件

> **上线要求：**若存在其他正式激活下游系统，也必须同步增加TEST关系过滤。


# 三十、上线策略

## 30.1 内部验证

配置内部测试组织和账号，使用少量设备验证完整链路，核查设备、云存和流量数据。

## 30.2 单个经销商灰度

选择一个经销商，配置少量测试账号并限制设备数量，观察误激活、权益和日志数据。

## 30.3 逐步开放

扩大经销商范围，开放正式申请审批，持续监控异常指标，并根据实际情况补充额度和风控规则。

| 真实用户是否能接管测试设备     | 是；正式校验通过后自动替换TEST关系     |

# 三十二、一句话需求定义

> **需求定义：**在用户中心账号和现有经销商组织体系基础上，为指定用户配置带有效期的经销商测试权限；测试账号通过任意APP添加设备时，仅创建TEST测试关系并授予基础测试能力，不执行设备正式激活、不写入首次激活时间、不触发云存和流量正式权益，同时记录完整免激活日志；设备交付真实用户后，真实用户可按现有流程正常完成首次正式激活。

# 三十三、审批流程设计（补充）

## 33.1 审批方式

测试账号的新增、重新申请等涉及权限准入的操作，统一通过**钉钉审批**完成。控制台负责发起申请和展示审批状态，不在控制台内部完成审批操作。

延期属于已审批权限的有效期维护操作，由平台运营人员在控制台直接处理，不发起钉钉审批，但必须记录操作人、延期原因、变更前后有效期和操作日志。

## 33.2 需要钉钉审批的操作

| **操作** | **触发场景** | **审批内容** |
|----------|-------------|-------------|
| 新增测试账号 | 提交新增表单 | 经销商组织、账号信息、有效期、申请原因 |
| 重新申请 | 从终态记录发起 | 同新增测试账号 |

## 33.3 不需要审批的操作

| **操作** | **理由** |
|----------|---------|
| 延期 | 已审批权限的有效期维护操作，平台运营人员直接处理并记录日志 |
| 暂停 | 收紧操作，走审批会在审批期间留下活跃权限的安全窗口 |
| 恢复 | 对已审批权限的重新激活，审批在新增时已完成 |
| 撤销 | 最强调收缩操作，即时生效以最大限度降低风险 |

## 33.4 钉钉审批流程

```
控制台提交申请 → 调用钉钉审批接口 → 权限记录进入"审批中"状态
                                         │
              钉钉审批人操作（通过 / 驳回 / 撤销）
                                         │
                                         ▼
                                    控制台接收回调
                                         │
              ┌──────────────────────────┼──────────────────────────┐
              ▼                          ▼                          ▼
           审批通过                   审批驳回                   审批撤销
              │                          │                          │
     创建/关联用户中心账号          权限记录 → REJECTED        权限记录删除或标记取消
     创建组织关系                    记录驳回原因
     创建权限记录 → APPROVED
     到达生效时间 → ACTIVE
```

## 33.5 审批回调处理

| **回调结果** | **控制台动作** |
|-------------|---------------|
| 审批通过 | 权限记录变为 APPROVED；创建或关联用户中心账号；创建组织关系；到达生效时间后自动变为 ACTIVE |
| 审批驳回 | 权限记录变为 REJECTED；记录驳回原因（从钉钉回调获取） |
| 审批撤销 | 权限记录删除或标记为取消 |

## 33.6 延期处理规则

延期不发起钉钉审批，由平台运营人员在控制台直接修改失效时间并即时生效。

理由：
1. 延期发生在已审批通过的测试权限上，属于权限维护，不是新增准入。
2. 平台运营人员需要在抽检周期变化时快速调整有效期，避免因审批等待影响既定测试。
3. 延期必须记录操作人、延期原因、变更前有效期、变更后有效期和操作时间。
4. 如果权限已经到期，应走重新申请流程，不直接修改原终态记录。

# 三十四、权限生命周期完整定义

## 34.1 状态机总览

```
新增/重新申请 → 审批中(PENDING) → 审批通过 → 待生效(APPROVED) → 到达生效时间 → 生效中(ACTIVE)
                     │                   │                                            │
                     ├──审批驳回→ REJECTED  ├──撤销(即时)→ REVOKED                     ├──延期(即时)→更新失效时间
                     │                   │                                            ├──暂停(即时)→ SUSPENDED
                     └──审批撤销→取消    └──到期→ EXPIRED                               │       ├──恢复(即时)→ ACTIVE
                                                                                       │       └──撤销(即时)→ REVOKED
                                                                                       ├──时间到期→ EXPIRED
                                                                                       ├──撤销(即时)→ REVOKED
                                                                                       └──组织停用→ 组织暂停(SUSPENDED)
                                                                                                    └──组织恢复→自动回到之前状态
```

## 34.2 终态定义

| **终态** | **含义** | **后续操作** |
|---------|---------|-------------|
| REJECTED | 审批驳回 | 重新申请 |
| EXPIRED | 有效期到期 | 重新申请 |
| REVOKED | 平台撤销（永久） | 重新申请 |
| 取消 | 审批被撤销 | 重新申请 |

终态记录不可修改，只能通过"重新申请"创建新的权限记录。

## 34.3 APPROVED 状态操作

APPROVED 状态下账号已创建但权限尚未生效，不存在活跃的测试绑定。可以执行撤销操作（即时生效），不会造成级联影响。

## 34.4 暂停与恢复的来源区分

| **暂停来源** | **触发方式** | **恢复方式** |
|-------------|-------------|-------------|
| 运营人员手动暂停 | 控制台操作 | 运营人员在控制台手动恢复 |
| 经销商组织停用 | 组织中心状态变更联动 | 组织中心恢复后系统自动恢复 |

运营人员手动暂停的权限，只能由运营人员手动恢复。组织停用导致的暂停，运营人员不能单独恢复——必须先恢复组织。

# 三十五、级联规则

## 35.1 权限变更对测试绑定的级联影响

所有导致权限从 ACTIVE 离开的事件，均触发统一的级联：

| **权限变更事件** | **权限目标状态** | **绑定级联目标状态** |
|-----------------|-----------------|---------------------|
| 时间到期 | EXPIRED | EXPIRED |
| 运营人员暂停 | SUSPENDED | EXPIRED |
| 运营人员撤销 | REVOKED | REVOKED |
| 组织停用 | SUSPENDED（组织来源） | EXPIRED |

级联规则：
- 在权限状态变更时即时执行，不延迟、不批量异步
- 禁止该权限下新增测试绑定
- 禁止继续发送设备控制指令
- 撤销测试访问权限
- 后续请求返回无权限
- 历史记录保留，日志不删除
- 控制台在权限状态变更的日志中记录级联影响的绑定数量

## 35.2 恢复后的绑定行为

暂停后恢复，被级联过期的测试绑定**不自动恢复**。测试人员需要重新扫码建立新绑定。重新扫码本身也是对设备状态的二次确认。

## 35.3 经销商组织状态联动

| **组织事件** | **权限影响** | **绑定影响** |
|-------------|-------------|-------------|
| 组织停用 | 该经销商下所有 ACTIVE / APPROVED 权限批量变为 SUSPENDED（标记来源为"组织停用"） | 所有 ACTIVE 测试绑定级联变为 EXPIRED |
| 组织恢复 | 标记来源为"组织停用"的 SUSPENDED 权限自动恢复为之前的状态 | 不自动恢复绑定 |
| 组织注销 | 该经销商下所有权限立即失效 | 所有 ACTIVE 测试绑定级联变为 EXPIRED |

## 35.4 用户中心账号异常联动

| **账号事件** | **权限记录变化** | **控制台展示** | **实际影响** |
|-------------|-----------------|---------------|-------------|
| 账号被冻结 | 权限记录状态不变（仍为 ACTIVE） | 行显示 ⚠️ 异常标记，tooltip 显示"关联用户账号已被冻结，测试绑定将被拒绝" | 绑定时被实时校验拦截（PRD 第十一章 11.1） |
| 账号被注销 | 权限记录状态不变（仍为 ACTIVE） | 同上 | 绑定时被实时校验拦截 |

不自动变更权限状态的理由：账号冻结可能是临时的（如安全审查），解冻后账号恢复。如果自动过期或撤销，解冻后无法恢复，必须重新申请——对一个临时事件付出永久代价。控制台用异常标记让运营人员知情，由运营人员决定是否手动暂停或撤销。

# 三十七、控制台页面结构

## 37.1 页面层级

```
经销商列表（一级视图）
  └── 经销商详情（二级视图）
        ├── 测试账号 tab
        ├── 测试设备 tab
        └── 操作日志 tab（经销商维度）

测试操作日志（全局视图，与经销商列表平级）
```

## 37.2 经销商列表

- **维度**：以经销商组织为主体，展示经销商基础信息和测试概览
- **核心字段**：经销商名称、编码、组织状态、测试账号数（有效/总数）、测试设备数、待审批数、最近测试时间、联系人
- **筛选**：经销商名称/编码（模糊搜索）、组织状态、是否有测试账号
- **操作**：点击行进入经销商详情

## 37.3 经销商详情

- **顶部**：经销商基础信息卡片（只读），展示名称、组织状态、编码、联系人、创建时间和三项统计指标
- **测试账号 tab**：按状态分组展示（待审批 → 待生效 → 生效中 → 已暂停 → 已终止），各组可折叠，行操作按钮根据权限状态动态显示
- **测试设备 tab**：分"测试中"和"已结束"两个区域展示
- **操作日志 tab**：预填经销商组织筛选条件的日志查询

## 37.4 全局测试操作日志

- 独立的日志查询入口，无预填筛选条件
- 支持按经销商组织、测试账号/用户ID、设备ID/SN、操作类型、操作结果、时间范围多维度筛选
- 比经销商维度的日志多一列"经销商"信息

## 37.5 日志操作类型覆盖

测试账号登录、测试绑定、激活抑制、权益抑制、测试解绑、权限变更、权限审批、真实接管、越权操作、兑换拦截、权限到期、设备控制
